你团队的架构决策散落在 飞书、Slack、微信、和几个资深工程师的脑子里。对人类来说这勉强够用——你可以问同事、搜聊天记录、翻文档。实在不行还能去茶水间堵人。
<Note>
但对 AI agent 来说，不在仓库里的信息等于不存在。
</Note>
## `Agent` 需要一份地图
所有需要的内容能够从地图出发去找到。一份在 `src/api/` 目录下、50 行的 `ARCHITECTURE.md`，比一份在 飞书里500 页但没人维护的设计文档有用一万倍。

## 怎么画好这张地图
1. **规则靠近代码。** 
	一条关于 API 端点认证的规则，应该放在 API 代码旁边每个模块目录下放一个简短的文档，说清楚这个模块的职责、接口和特殊约束。
 2. **使用标准化的入口文件。** 
	`AGENTS.md`（或 `CLAUDE.md`）是 agent 的"着陆页"。它不需要包含所有信息，但必须能让 agent 快速回答"这是什么项目"、"怎么跑"、"怎么验证"这三个问题。50-100 行就够了。
1. **最小但完备。** 
	每条知识都应该有明确的使用场景。如果你删掉某条规则不影响 agent 的决策质量，那这条规则就不应该存在。
2. **规则与代码一起更新**
	把规则文档放在对应的模块目录里。改代码的时候自然会看到文档，改代码之后 CI 提醒你检查文档是否需要更新。
	```markdown
project/
├── AGENTS.md              # 入口：项目概览、运行命令、硬约束
├── src/
│   ├── api/
│   │   ├── ARCHITECTURE.md  # API 层的架构决策
│   │   └── ...
│   ├── db/
│   │   ├── CONSTRAINTS.md   # 数据库操作的硬约束
│   │   └── ...
│   └── ...
├── PROGRESS.md             # 当前进度：做了什么、在做什么、被什么阻塞
└── Makefile                # 标准化的操作命令：setup、test、lint、check
	```
## 用 ACID 原则管理状态
- **原子性**
	每次"逻辑操作"（比如"添加新端点并更新测试"）用一个 git commit 原子化。中途挂了就 `git stash` 回滚。
- **一致性**
	定义"一致状态"的验证——所有测试通过、lint 无报错。Agent 每次操作后跑验证，不一致的中间状态不要 commit。
- **隔离性**
	多个 agent 并发工作时，状态文件要避免竞争条件。简单方案：每个 agent 用独立的进度文件，或者用 git 分支（worktree）隔离。
- **持久性**
	关键的项目知识用 git 跟踪的文件（如每个模块下的指引文档）持久化。临时状态可以只在会话内存里，但跨会话必须的知识必须写到文件里。脑子里的不算，写在纸上的才算。
